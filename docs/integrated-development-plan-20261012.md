# 낙뢰방호장치 통합 개발·검증 계획

작성일: 2026-10-12

상태: 2026-10-12 PC 기능·학습·재생·모델 변환·portable host 검증을 실행했다. 실제 숫자와 요구별 상태는 [통합 검증 결과](integration-results-20261012.md), 실행법은 [통합 실행 가이드](integration-usage.md)에 기록했다. 아래는 당시 계획이며 실제 장치와 물리 성능의 미확정 조건은 계속 적용한다.

이 문서를 다음 전체 작업의 기준으로 사용한다. 앞서 작성한 [타임라인·데이터·오경보 계획](realtime-timeline-evaluation-plan-20261012.md)의 요구를 포함하며, 미구현 기능·모델 변환·임베디드 연결·통합 검증까지 확장했다. 기존 원본 데이터·모델·보고서·발표자료는 보존한다.

## 1. 기존 계획으로 보완되는 문제와 추가할 문제

기존 계획은 센서 기준 해석, 데이터의 수와 다양성, 오경보 정의, 실제 시간 흐름과 평가 방법을 보완한다. 성능 개선 여부는 새 평가 결과로 확인해야 한다. 합성 데이터를 늘리거나 경보를 늦게 내보내는 것만으로 실제 낙뢰 성능이 개선되었다고 결론 내릴 수 없다.

| 문제 | 대응 | 확인 조건 |
|---|---|---|
| 초과/미달·온도 기준의 의미 미확정 | 명시적 단위·비교 연산자·경계·기준 온도·근거를 설정 | 장치 사양과 회사 확인 |
| 명시 규칙이 없으면 threshold에 `ge`를 적용하는 경로 | 자동 방향 추정을 제거하고 확인된 규칙만 활성화 | 경계·미확정 규칙 테스트 |
| 작은 합성 데이터와 제한적인 위험 이벤트 | 독립 시나리오 확대, 장시간 정상 기록, 실측 확보 | 독립 세션·이벤트 수와 출처 보고 |
| 시퀀스 FP를 경보 횟수처럼 해석 | 입력·경보 에피소드·시간·이벤트 평가를 분리 | 시간 구간과 정답 매칭 검증 |
| 단순 Logistic보다 LSTM이 좋다는 근거 부족 | 같은 조건에서 규칙·Logistic·LSTM 비교 | validation 선택과 새 Test 평가 |
| 학습 모델과 실시간 특징/단위/정규화 불일치 가능성 | 버전 있는 입력 계약과 공통 변환 사용 | 배치/연속 입력·출력 일치 |
| 기존 16×20 모델과 표준 후보 입력의 차이 | 입력을 바꾸면 dataset·scaler·모델·buffer 함께 갱신 | 호환되지 않는 묶음 로딩 거부 |
| 짧은 입력에서 느린 센서의 장기 추세 확인 불가 | 현재값·age를 사용하고 필요한 경우 과거 장기 특징 추가 | 길이별 검증과 시간 단위 테스트 |
| 센서·통신 장애가 정상 판단으로 이어질 위험 | 핵심 입력·신선도 정책과 판정 불가 상태 | 장애가 경보 해제를 대신하지 않는지 검증 |
| 미래 예측과 현재 상태 감지의 혼동 | target과 horizon을 명시 | 미래 예측은 별도 정답·선행 시간 평가 |
| 링 데모가 알려진 event_id에서 상태를 초기화 | 실시간은 획득 시작·재시작 정책만 사용 | event_id를 지워도 연속 동작 |
| 학습의 이벤트별 초기화와 실제 연속 운용의 차이 | 획득 세션 경계를 명시하고 연속 held-out 구간으로 검증 | 사건 전후를 끊지 않은 입력 평가 |
| 고정 링 배열만으로 전체 메모리를 판단 | 원본 기록·입력·큐·arena·stack·firmware까지 집계 | PC/host C++/MCU 수치 구분 |
| 이벤트 저장 중 수신·추론이 멈출 위험 | 제한된 큐와 분리된 저장 작업 | 저장 지연·실패 중 연속 입력 테스트 |
| LSTM 런타임의 상태가 창 사이에서 유지될 가능성 | 현재 stateless 창 단위 학습과 같은 상태 정책 | 같은 입력 반복·A/B/A 실행 비교 |
| 양자화 후 경계 판정이 달라질 가능성 | 출력 오차·판정 변화·FN/FP·경보 시점을 비교 | 변환 모델별 검증 및 고정 Test |
| 장치별 재사용 event_id의 처리 차이 | 장치·획득 세션·이벤트 식별 기준을 일관되게 관리 | split과 평가의 ID 충돌 테스트 |

현재 학습·데이터 분할은 event_id를 전역 식별자로 취급하는 경로가 있고 이벤트 평가에는 device_id도 사용한다. 다중 장치 데이터에서는 전역 고유 ID를 만들거나 복합 키를 일관되게 사용하도록 정리한다. ID와 정답 metadata는 모델 특징으로 사용하지 않는다.

## 3. 판정 기준과 정답 정책

센싱 범위, 센서 위험 규칙, 정답 label, AI 경보 규칙을 분리한다. 제공 자료의 기준값 2, 1 mA, 25℃, 60%는 보존하고 연산자와 의미가 확인된 항목만 운영한다.

규칙에는 물리량·단위·상한/하한/양방향·경계 포함 여부·지속 시간·해제 조건·온도 비교 기준·AND/OR 조합·staleness·근거·버전을 포함한다. 변화율과 차이에는 확인된 별도 기준값이 필요하다. 누설전류와 온도 기준은 센싱 범위 하한과 같으므로 의미를 확인한다. H/L 인코딩만으로 실제 위험 정답을 확정하지 않는다.

| 정답 | AI 판단 | 평가 |
|---|---|---|
| 정상 | 정상 | TN |
| 정상 | 위험 | FP: 오경보 |
| 위험 | 정상 | FN: 미탐지 |
| 위험 | 위험 | TP |

이 네 경우를 센서 위험 조건의 충족/미충족으로 다시 나누어 8가지 조합을 분석한다. 초과·미달·동일값, 순간 이탈·지속 이탈, 온도 상승량, 복합 센서 조건, 회복과 입력 장애를 구분한다. label이 없거나 입력을 판정할 수 없으면 FP/FN의 정상 분모로 넣지 않고 별도로 집계한다.

AI와 같은 규칙으로 만든 정답을 평가한다면 '규칙 재현 실험'으로 표시한다. 실제 낙뢰 성능은 독립적인 실측·실험 정답을 사용한다. 현재 label_horizon_seconds=0인 감지와 미래 예측을 분리한다. 미래 예측에는 예측 사건·horizon·선행 경보 허용 구간이 추가로 필요하다.

실시간 출력은 첫 버전에서 이진 정상/위험 알림과 입력 준비/판정 불가 사유를 사용한다. 이미 지원하는 multiclass 학습은 의미가 확인된 실제 label에 대해서만 활성화한다. 모델 점수는 보정·검증 없이 실제 낙뢰 확률로 설명하지 않는다.

## 4. 데이터 확대와 실험

| 학습·평가용 시나리오 | 초기 목표 |
|---|---:|
| 정상·정상 잡음 | 20개 |
| 기준 미달·동일·초과 주변 | 10개 |
| 단일 센서 변화 | 10개 |
| 복합 센서 변화 | 10개 |
| 위험 전환·회복·반복 경보 | 10개 |
| 입력·통신 오류: 별도 검증 | 추가 10개 |

60초·100 ms 기준이면 총 약 42,000행이다. 이는 초기 소프트웨어 개발 목표이다. 학습·평가 60개 구간의 초기 분할은 36/12/12이며, 오류 10개는 품질·판정 불가 시험에 사용한다. 실제 정렬·제외 후의 원본/유효 관측/시퀀스/분할·클래스/독립 세션·이벤트 수를 다시 집계한다.

seed·파형·변화 시점·잡음·채널 상관관계를 다양화한다. 모든 센서가 동일한 합성 파형을 따라 움직이는 데모 구조에서 발생할 수 있는 쉬운 분류 단서를 점검한다. 같은 데이터 복사나 중복 창을 독립 사례로 세지 않는다. 물리 단위의 시험값과 기존 임의 단위 fixture를 명시적으로 구분한다.

초기 분할은 시간순으로도 정상·위험과 주요 조건이 적절히 포함되도록 만들고 검증한다. 기존 split 구현이 그룹을 시간순으로 나누므로 시나리오 종류별로만 순서대로 저장해 분할별 분포가 갈리는 것을 방지한다. 유사 생성 패턴·같은 획득 세션의 다른 구간은 분할에 흩어지지 않도록 관리한다. 시간 분할에서는 가장 긴 후보 입력·과거 특징·label horizon을 고려한 공통 purge 정책을 사용한다.

장시간 정상 연속 재생과 느린 센서 업데이트 테스트를 추가한다. 이후에는 장치·날짜·환경별 정상 기록과 확인된 실제 위험 이벤트를 확보한다. 합성과 실측 결과는 따로 보고하며, 실제 운용 클래스 비율의 평가도 남긴다.

모델 실험은 Logistic과 작은 단방향 LSTM을 유지한다. hidden 16/32/64, 입력 길이와 특징 축소를 config 기반 실험 목록으로 지원하되 초기 실행은 제한된 후보부터 시작한다. 비교에 같은 raw 분할과 공통 평가 구간을 사용하고 후보별 coverage도 보고한다. 선택은 validation, 최종 확인은 새 Test에서 수행한다. INT8 보정용 대표 데이터도 Train에서 선정한다.

최적 checkpoint·LR 감소·early stopping과 학습 예산 도달 표시를 유지한다. 후보를 여러 seed로 재확인하고 독립 그룹 단위 성능 변동을 보고한다. epoch 수 증가만으로 충분한 성능이라고 판단하지 않는다. 변환 가능성은 기존 작은 모델로 먼저 시험하여 많은 재학습 후에 지원 불가를 발견하는 비용을 줄인다.

## 5. 미구현 기능별 구현 계획

### 5.1 입력 수신·검사·실시간 전처리

CSV/Parquet 입력과 가상 sensor reader를 먼저 연결한다. 실제 UART/CAN 등 통신 adapter는 확인한 규격에 맞춰 추가한다. 일반 모니터링과 고속 surge는 별도 source로 유지하고 surge를 임의로 100 ms에 맞추지 않는다.

관측 시각·수신 시각·장치·출처·상태를 포함하는 입력 구조를 사용한다. 빈 셀의 비관측과 명시적 무효값을 구분하고 기존 timestamp·numeric·상태 검사 규칙을 재사용한다. 필요한 경우 행 검사 핵심만 기존 품질 검사에서 분리해 배치와 수신 처리에 함께 사용한다.

실제 adapter에서 같은 관측 시각의 서로 다른 센서 패킷을 받는 경우에는 확인한 규격에 따라 하나의 sparse 관측으로 모아 aligner에 전달한다. 동일 센서의 중복 패킷과 다른 센서의 동시 관측을 구분한다. 이미 정렬한 과거 시각에 늦게 도착한 입력은 임의로 과거 판정을 다시 쓰지 않고 명시한 late-input 정책으로 처리한다.

기존 CausalAligner, FeatureTransform, FrozenScaler를 연결한다. scaler fit을 실시간에서 호출하지 않는다. 핵심 센서·staleness·현재값/age/mask 정책을 명시하고 불가 구간은 입력을 보류한다. 느린 센서 값을 새 원본 관측으로 복제하지 않는다.

첫 core는 단일 stream 소유자가 변환·링·시퀀스 상태를 갱신한다. 입력 큐와 writer 큐에 한도를 설정하고, 최대 처리 가능 장치 수를 명시한다. 여러 장치를 받으면 장치별 상태를 분리하거나 지원하지 않는 입력을 명확히 거부한다. 늦은 패킷·중복·역순·큰 공백·큐 초과의 정책과 집계 사유를 남긴다.

완료 조건: 연속 입력이 준비 상태와 판정 불가 사유를 생성하고, 배치/연속 특징과 정규화 결과가 같으며, 정답 event_id 없이 실행한다.

### 5.2 InferenceEngine과 모델 묶음

모델·scaler·feature 순서·단위·입력 shape·정렬 간격·label/class 순서·전처리 설정·해시를 하나의 manifest로 연결한다. 운영 시 로딩 단계에서 계약을 검사하고 불일치하면 추론을 시작하지 않는다. 초기 버전에서는 실행 중 묶음을 임의로 교체하지 않는다.

Keras와 Logistic의 PC 추론부터 연결하고 검증한 LiteRT backend를 추가한다. SequenceBuilder가 READY인 경우에만 입력 workspace를 사용한다. 실패 상태에 남은 이전 tensor를 재사용해 추론하지 않는다. 모델 NaN/Inf·잘못된 shape·호출 실패·점수 오래됨은 정상 점수로 대체하지 않는다.

출력은 입력 구간 종료 시각·수신/추론/판단 시각, risk_score, predicted_class, model_version, inference latency와 입력 유효성 사유를 포함한다. 현재 LSTM의 창 단위 stateless 의미를 유지하며 LiteRT 내부 변수 상태도 창 사이에서 의도치 않게 유지되지 않는지 확인한다.

완료 조건: 저장 모델과 연속 입력의 결과가 배치 기준 결과와 일치하고, 입력 계약 오류·이전 tensor·잘못된 모델 출력을 거부한다.

### 5.3 DecisionEngine

risk_on_threshold, risk_off_threshold, 연속 확인 횟수 또는 지속 시간을 명시한다. 1차 구현에서는 한 가지 지속 조건을 명확히 선택하고, 적용한 추론 간격을 함께 기록한다. 경계의 동일값 처리를 고정하고 validation에서 선택한 값을 사용한다.

NORMAL / RISK 상태와 입력 준비·판정 불가 상태를 구분한다. 입력 장애 중 기존 경보를 해제할지 유지할지는 운용 정책으로 확정한다. 최소한 장애가 정상 점수나 해제 확인 횟수로 들어가지 않게 한다. 새 정상 관측을 받은 뒤 필요한 연속 유효 구간을 확보해야 재개한다.

advisory를 기본으로 유지하고 실제 actuator는 stub/interface로 제공한다. 기존 하드웨어 안전 로직을 유지한다. 확인된 물리 규칙 경보와 AI 알림은 출처와 이유를 각각 기록한다.

완료 조건: 경계 진동·짧은 양성·지속 위험·회복·장애·재연결에서 진입과 해제가 정의대로 작동하고, 하드웨어 출력이 자동으로 활성화되지 않는다.

### 5.4 EventRecorder

경보가 발생하면 pre-event 원본·전처리 특징, 감지 순간, post-event 입력·점수·상태를 보존한다. 현재 feature ring에는 원본 관측이 없으므로 원본용 bounded history도 준비한다. 원본과 특징을 역정규화 값 하나로 대체하지 않는다.

기록 구간의 기준 시각이 경보 시각인지 확인된 실제 사건 시각인지 명시한다. 실제 사건 시각이 나중에 확인되면 별도 annotation으로 연결한다. event_id는 수신 시스템이 생성한 경보 ID와 정답 사건 ID를 구분한다.

event에는 원본 단위·출처·timestamp, processed values, risk_score, predicted_class, model/scaler/rule 버전, decision threshold, 입력 유효성, 누락 사유, ground_truth=UNLABELED를 저장한다. 추후 정답을 추가하는 과정은 입력 특징에 영향을 주지 않는다.

post-event 수집은 수신 흐름에서 계속 진행하고 파일 쓰기는 제한된 큐의 별도 writer에 맡긴다. 링은 한 소유자만 읽고 수정하며 writer에는 분리된 복사본/제한된 chunk를 전달한다. 활성 이벤트 수·최대 길이·병합 정책·큐 용량·파일 보존량을 설정해 반복 경보로 메모리와 디스크가 계속 커지지 않게 한다.

파일 실패·writer 적체·종료·CSV EOF로 post-event가 부족한 경우 partial/incomplete와 사유를 기록한다. 임시 파일의 검증 후 원자적 저장을 사용하고 기존 원본·다른 이벤트를 덮어쓰지 않는다. 저장 실패를 숨기지 않으며 추론 경로가 저장 완료를 기다리지 않게 한다.

완료 조건: pre/post 구간·원본·모델 버전이 보존되고, 기록 중 추론이 계속되며, 겹치는 경보·queue full·저장 실패·중간 종료가 정해진 정책으로 처리된다.

### 5.5 연속 재생과 실행 CLI

현재 최대속도 buffer_demo와 별도로 전체 replay를 구현한다. 1x/2x/10x/max를 지원하고 관측 시간축은 보존한다. 가상 시계와 대기 함수를 분리하여 자동 테스트에 긴 sleep이 필요하지 않게 한다. wall-clock 처리 지연과 가상 시각의 감지 지연을 따로 보고한다.

fault injection은 늦게 도착한 정상 timestamp와 잘못된 timestamp를 구분한다. 재생 전에 전체를 정렬해 지연·역순 오류가 사라지지 않게 한다. 알려진 label/event_id는 평가에만 쓰며 입력 준비나 상태 초기화에 쓰지 않는다.

단계별 CLI를 제공하고 기존 inspect/build/train/evaluate 명령을 재사용하는 통합 runner를 추가한다. 설정과 실험 ID를 받아 확대한 데이터 준비, 학습, export, replay, 평가·보고서를 같은 run directory에 연결한다. 필요한 단계 실패에는 실패 상태와 종료 코드를 남긴다. 선택적 형식의 지원 불가도 성공으로 기록하지 않는다. 재실행은 새 버전 경로를 사용한다.

완료 조건: 하나의 실험 명세로 전체 결과와 해시·설정·로그가 연결되고, 같은 가상 입력에서 재생 배속에 따른 특징·점수·경보 시각 차이가 허용 정책 안에 있다. 수신 적체·실제 시간 초과는 별도 집계한다.

### 5.6 경량화·SavedModel/LiteRT export

SavedModel과 LiteRT float32/float16/int8 변환 경로를 구현한다. 고정 batch=1 입력 계약, 필요한 연산자와 버전, runtime·converter 버전을 기록한다. 설치된 TensorFlow/Keras와 공식 지원 경로를 확인한 뒤 호환 조합을 lock에 고정한다.

INT8 representative dataset은 Train의 실제 전처리 입력에서 선정한다. scale/zero-point, 입력 rounding·clip, 출력 역양자화를 manifest와 runtime에 연결하고 saturation을 집계한다. float fallback이 남은 파일을 완전 INT8이라고 표시하지 않는다.

검증은 평균/최대 출력 오차뿐 아니라 임계값 주변 판정 변화, FN/FP, 실제 경보 시점·지속 시간까지 포함한다. 형식별 threshold를 재검증해야 한다면 validation만 사용하고 최종 Test에서는 고정한다. 허용 성능 저하와 자원 조건에 따라 validation에서 배포 후보를 선택한 뒤 보호한 Test로 최종 확인한다. Test 결과를 보고 다음 후보를 재선택하지 않는다.

일반 LiteRT 변환 성공과 MCU kernel 지원은 각각 확인한다. Flex/SELECT_TF_OPS나 unresolved/custom op가 필요한 경우 MCU 준비 완료로 표시하지 않는다. 변환 실패의 연산자·shape·원인을 보고하고, 우선 단방향 LSTM 구조·고정 shape를 조정한다. MCU 제약이 확인될 때만 GRU/1D CNN 등 대안을 별도 실험으로 검토한다.

완료 조건: 요청 형식별 SUCCESS/UNSUPPORTED/FAILED와 원인을 보고하고, 성공 파일은 실제 interpreter에서 로딩·실행·출력 비교를 통과한다. 변환 파일 생성만으로 검증 완료라 하지 않는다.

### 5.7 MCU 자원 보고서·portable C/C++ 연결

target_mcu 설정을 확장해 실제 Flash/RAM, 예약 영역·여유 예산, CPU/architecture, 허용 처리 지연, toolchain을 입력받는다. 값이 없으면 feasibility=UNKNOWN을 유지한다.

Flash는 모델 C 배열과 연산자 runtime·전처리·firmware를 포함해 평가한다. RAM은 feature/raw ring, input workspace, tensor arena와 포함된 state/scratch, queues, recorder buffers, stack, firmware 여유를 집계한다. arena 내부 항목을 바깥에서 다시 더하는 중복 계산도 피한다. 모델 파일 크기와 float32 가중치 크기를 전체 RAM으로 해석하지 않는다.

모델 byte array, feature 순서·scaler 상수·규칙과 양자화 상수를 생성한다. portable C/C++에서 고정 배열 링·입력 조립·선택한 인과적 특징·정규화·판단을 구현하고 PC golden vectors와 비교한다. PC의 pandas/NumPy 구현이 MCU 코드에서 그대로 작동한다고 가정하지 않는다.

timestamp 단위·시간 간격·clock wrap·restart 정책을 포트에 명시한다. 학습과 동일한 stateless 추론 상태를 유지하며 필요 kernel만 등록한 MCU runtime을 연결한다. 실제 센서와 actuator는 adapter 경계로 둔다.

보드에서는 실제 tensor arena, 전체 RAM/Flash, 평균·p95·관측 최대 처리시간, deadline 초과, 입력 누락, 장기 실행을 측정한다. host C++ 결과와 PC 지연을 MCU 수치로 대신하지 않는다. 실제 최악 시간 보장은 목표 환경의 추가 조건과 측정이 필요하다.

완료 조건: host 빌드와 golden vector 일치, 실제 지원 kernel 확인, 목표 장치 예산과 처리 기한 충족. 보드가 없는 동안은 portable 코어·시험 자료·UNKNOWN 보고서까지 완료 범위로 분리한다.

## 6. 오경보 평가와 타임라인 산출물

입력 FP/FN, 경보 에피소드, 시간당 오경보, 정상 시간의 경보 활성 비율, 이벤트 탐지율·미탐지, 감지 지연, 판정 가능 비율을 보고한다. 정상 유효 시간·전체 운전 시간·판정 불가 시간도 같이 남겨 입력을 많이 버려 FP가 낮아지는 경우를 확인한다.

경보 episode의 진입·해제·병합과 정답 이벤트 매칭을 시험 전에 고정한다. 현재 감지에서 미래 예측의 선행 허용 구간을 자동 적용하지 않는다. 평가 분모가 없으면 계산 불가로 표시하고 겹치는 windows를 독립 사건으로 보지 않는다.

타임라인은 같은 시간축의 센서값·확정 기준선, 모델 점수·on/off 임계값, 정답·경보·판정 불가 구간으로 구성한다. 관측·수신·입력 준비·추론·판단·저장 시각과 지연을 연결한다. 시계가 동기화되지 않은 관측/수신 시각을 단순 차감해 실제 전달 지연으로 주장하지 않는다.

기존 합성 FP 46과 새 결과를 각각의 모델·데이터 버전으로 표시한다. 기준 주변 정상 잡음, 순간/지속 이탈, 복합 조건, 회복, 장애와 새 환경별 사례를 보여준다. 모델·threshold·지속 조건 선택은 validation, 최종 비교는 보호한 새 Test에서 수행한다.

| 회귀 | 관련 새 테스트와 기존 전체 테스트, 원본/기존 모델 보존, 저장·재로딩·run manifest 재현 |

정확한 숫자 목표가 미확정이면 임의의 '합격 성능'을 붙이지 않는다. 정답 정책과 허용 recall/FPR·경보 부담·지연·자원 예산을 확정한 뒤 통과 여부를 판정한다. 기능 테스트 통과와 실제 장치 성능 통과를 분리한다. 테스트 개수의 증가만으로 검증 범위가 충분하다고 판단하지 않는다.

PC 완료는 정상·위험·장애의 전체 수신/추론/판단/기록 재생이 작동하고, 오경보 지표·계약 검사·저장 실패 처리·재현 실행이 확인된 상태이다. MCU 완료는 해당 보드에서 kernel·출력·자원·처리 기한이 실제 확인된 상태이다. 실제 낙뢰 성능 완료는 독립 실측 정답과 합의한 운용 요구로 확인한 상태이다.

## 9. 필요한 외부 정보와 나중에 확정할 범위

| 필요한 정보 | 영향을 받는 작업 | 정보 없이 진행 가능한 범위 |
|---|---|---|
| 센서 기준 방향·단위·온도 기준 | 물리 규칙 운영·정답 해석 | 명세·validation 코드·합성 경계 테스트 |
| 실제 데이터와 label/onset 정의 | 실측 재학습·실제 FP/FN·선행 예측 | software fixture·annotation 양식·평가 코드 |
| 허용 경보·미탐지·지연 | 배포용 임계값과 지속 조건 | validation 절충 표와 후보 비교 |
| UART/CAN 등 패킷·상태·시간 규격 | 실제 SensorReader adapter | CSV/가상 reader와 adapter 경계 |
| MCU·보드·예산·toolchain | firmware·장치 resource 완료 | export·portable C/C++·UNKNOWN 보고 |
| 고속 surge 스키마 | 별도 고속 source adapter | source 격리·수신 인터페이스 |

장기 온습도 추세, 미래 낙뢰 예측, 확인하지 않은 multiclass 의미와 대체 모델은 해당 목적·데이터·MCU 제약에 따라 활성화한다. 인터페이스와 확인 항목은 계획에 포함하되 검증 근거 없이 완료 기능으로 발표하지 않는다.

## 10. 산출물과 PPT 반영

새 run directory에 데이터·분할·실험 설정/해시, 모델 bundle, training history·선택 근거, 변환별 파일·검증·operator 보고서, replay predictions·decisions·events, 입력/시간/이벤트 평가, timeline 그림, resource report, 테스트·재현 결과와 남은 확인 항목을 연결한다.

최종 실행 가이드는 새 환경 준비, 데이터 QA/build, 학습·실험 비교, export, 전체 replay, 평가와 보고서 생성 명령을 설명한다. 제안 CLI 경로는 구현 후 실제 실행한 명령으로 확정한다. 구현되지 않은 명령을 현재 실행법처럼 제공하지 않는다.

PPT는 기존 11장 흐름에서 2번을 센서 판정 기준, 3번을 실제 확대 데이터 수, 4·5번을 링·전체 타임라인, 8·9번을 오경보 정의·조건별 사례, 10번을 모델 비교·검증 범위, 11번을 실제 남은 작업으로 갱신한다. 새 수치를 측정하기 전에는 목표로 표시한다. 제출 보고서·발표자 노트·대본의 구현 범위와 숫자를 같은 run의 실제 결과로 맞춘다.

각 단계 종료 때 변경 파일, 설계 이유, 실제 실행법, 테스트 결과, 남은 작업을 기록한다. 전체 작업은 위 완료 수준과 요구별 증거를 검토한 뒤 마무리한다.

## 11. 확인한 근거

프로젝트: README, 기존 타임라인 계획, `src/realtime`의 ring/sequence/demo, `src/preprocessing`의 공통 변환·설정 검증, `src/models/lstm.py`와 `baselines.py`, `src/training/data.py`, `src/dataset/split.py`, `src/evaluation/metrics.py`, `configs/model.yaml`·`preprocessing_standard.yaml`·`realtime.yaml`·`target_mcu.yaml`, 최초 사용자 요구의 PHASE 4~6 범위.

공식 자료:

- Keras LSTM에서 LiteRT 융합 연산자로 변환하는 경로를 제공한다. 실제 사용 버전·모델의 변환과 MCU kernel을 검증한다. [Google RNN 변환 문서](https://developers.google.com/edge/litert/conversion/tensorflow/rnn)
- 대표 입력을 사용하는 정수 양자화와 float fallback의 차이를 확인했다. 프로젝트는 Train 대표 입력, 실제 dtype·op 검사, 출력 비교를 적용한다. [Google 정수 양자화 문서](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant)
- MCU runtime은 제한된 연산과 수동 메모리 관리를 전제로 하므로 일반 PC 변환 성공을 장치 탑재 완료로 보지 않는다. [Google MCU 개요](https://developers.google.com/edge/litert/microcontrollers/overview)
- tensor arena는 여러 할당 영역과 runtime 정보를 포함한다. 실제 arena 기록과 전체 firmware 메모리를 구분해 측정한다. [TFLM 메모리 관리 공식 저장소 문서](https://github.com/tensorflow/tflite-micro/blob/main/tensorflow/lite/micro/docs/memory_management.md)
- 모델/임계값 선택과 train-only 변환은 독립 평가를 보호하는 원칙을 유지한다. [scikit-learn 임계값 문서](https://scikit-learn.org/stable/modules/classification_threshold.html), [데이터 누출 방지 문서](https://scikit-learn.org/stable/common_pitfalls.html)
